# 04 技术框架

> 这一版框架不是从零设计的，是**从已经跑通的代码里长出来的**。
> `src/data/` + `src/sim/` 这套"数值真源 + 无渲染哨兵"的结构已经在用，
> 本文要做的是把它扩成一个能跑的游戏，而不是换一套新架构。

---

## 1. 最重要的一条架构决定：模拟器**不**升级成引擎

最省事的做法是"把 `src/sim/` 加个渲染层，直接变成游戏"。
**不这么做**，理由是它已经在 §10 被实测证伪过一次：

| 模拟器简化 | 变成引擎时必须做的事 |
|---|---|
| 一维距离 | 二维空间 + 寻路 + 包围 |
| 单点索敌 | 多目标 + 空间分区 |
| 队员不走位 | 走位、牵引、地形回避 |

要让 `sim/` 撑起这些，它就得引入寻路、空间索引、地形——
而这些恰恰是它**现在能跑得比游戏快 1000 倍**的原因。
把哨兵改造成引擎，等于同时失去哨兵和引擎。

**边界定在这里：**

```
src/data/   ← 唯一共享层。策划案、模拟器、游戏三者共用的数值真源
src/sim/    ← 只给平衡用。无渲染、无寻路、批量化。永远不 import three
src/core/   ← 游戏逻辑。无渲染，但【有】二维空间、寻路、地形
src/game/   ← Three.js 渲染。只读 core 的状态，不改
src/ui/     ← DOM 覆盖层（HUD / 结算 / 小队面板）
```

`sim/` 和 `core/` **不互相 import**。它们各自 import `data/`。
这样"改了数值表，模拟器读数和游戏行为一起变"，但两边的实现可以完全不同。

> **代价**：同一套伤害公式会有两份实现（`sim/combat.ts` 和 `core/`）。
> 这是刻意的取舍——共享公式会逼着两边互相迁就，
> 而它们要回答的问题本来就不一样（"数值自洽吗" vs "打起来什么样"）。
> 防漂移的手段不是共享代码，是 §4 的**对账测试**。

## 2.1 元层：`meta/` 为什么单独存在（本轮新增）

长期成长线（解锁关卡 → 换阵容 → 通关下一关）需要**跨局持久化**的状态。
它不能放进 `core/`——`core/` 是"一局之内"的世界状态，随 run 结束销毁；
也不该放进 `ui/`——存档是逻辑，不是界面。

所以新开一层 `meta/`，与 `core/` `sim/` 同级，同样**禁止 import `three`**
（同一个 ESLint 规则覆盖），并且**只 import `data/`**。

```
meta/profile.ts   →  import { SCENES, SCENE_BY_ID, expandScene } from '../data/scenes.ts'
                  →  import { HEROES, WEAPONS } from '../data/characters.ts'
                  ✗  绝不 import core/ game/ ui/
```

**依赖方向是单向的**：`data/` ← `meta/` ← `ui/`。
`core/` 不认识 `meta/`——一局怎么打，与"这个玩家解锁了什么"无关。
衔接点在 `game/main.ts`：读 `meta` 决定加载哪个子关卡，把
`expandScene(scene, difficulty)` 的结果**当成参数**交给 `core/`。

### 2.1.1 存档 schema

```ts
type Profile = {
  version: 3;                          // ★ 必须有，否则改结构时老存档无法迁移
  cleared: string[];                   // 已通关的子关卡 id（'jungle-07'），82 关的进度真源
  stars: Record<string, 0|1|2|3>;      // ★ v3：key = `${关卡 id}@${难度}`。技能点只由"新星"产出
  unlockedHeroes: string[];            // 角色 id
  owned: { weapons: WeaponId[]; items: BuffId[] };  // ★ v3：军械库，买断、全队共享
  loadouts: Record<string, { weapon: WeaponId; item?: BuffId }>;  // ★ v3：每人出战配置，canEquip 校验
  skillPoints: number;                 // 同一批点管技能等级与专精树
  specs: Record<string, string[]>;     // 角色 id → 已点开的节点 id
  advanced: Record<string, boolean>;   // ★ v3：高级技能是否已购（军衔门槛另算）
  money: number;                       // 局外货币余额（每局结算带出）
  honor: Record<string, number>;       // ★ v3：按角色累计（结算时 honorPerHero 均分）；军衔由 rankAt 现算
};
```

**跨关继承的白名单就是这张表**（用户裁决 #6）：军衔（`honor`）、技能（`specs` / `advanced`）、
军械库（`owned` / `loadouts`）。等级、武器阶、临时武器、拾取的增益**不进存档**。

**v2 → v3 的迁移**：`unlockedWeapons` / `unlockedItems` → `owned`；`ranks` 删除（由 `honor` 现算）；
`honor` 总数按当时参战名单均分成按角色的记录；`stars` / `loadouts` / `advanced` 补空。

三条规则：

1. **`cleared` 存关卡 id，不存"进度百分比"。** 关卡 id 由 `scenes.ts` 推导，
   是稳定的；百分比会在关数变化时失准（上一轮就动过 15 → 13）。
2. **`owned` 存种类，不存阶。** 军械库买的是装备本身——
   武器阶由等级自动带动（`weapons.ts` 的 `tierForLevel`），存档里没有它的位置。
   局内**零购买**（A25），所以存档里也**不该有**任何"当前等级/当前阶"的字段。
3. **`specs` 存节点 id，不存效果。** 效果从 `characters.ts` 的
   `specialization` 现算——否则改一次节点数值就要迁移全部存档。

存档落地方式由 M3 决定（`localStorage` 或文件），本节只钉 schema。

### 2.1.2 为什么专精不能进伤害公式（这条约束是编译器执行的）

`meta/` 会往 `core/` 传一个角色列表。很自然的想法是"顺便把专精效果也传进去"——
**不能。** 原因在 §4 的对账测试。

```
core.computeDamage(...)   与   sim.computeDamage(...)   签名必须完全一致
                          ↑
      前提是：伤害只由「属性 / 等级 / 武器阶 / 技能参数 / 目标护甲」决定
```

专精的效果被**限定在公式的输入侧**：

```ts
export type SpecEffect =
  | { kind: 'attr'; ... }        // 改属性   → 改了公式的输入
  | { kind: 'weaponTier'; ... }  // 改武器阶 → 同上
  | { kind: 'skill'; ... }       // 改技能参数 → 同上
  | { kind: 'ai'; ... }          // 改 AI 参数 → 不进公式
  | { kind: 'answer'; ... }      // 加维度答案 → 不进公式
  | { kind: 'revive'; ... };     // 复活次数 → 不进公式
```

**里面刻意没有"新增伤害乘区"这个变体。** 所以专精满点的角色对 `computeDamage`
而言，就是一个"属性更高、武器阶更高、技能参数不同"的普通角色——
签名没变，对账测试继续成立。

**这条由 TypeScript 联合类型执行，不是靠注释提醒。** 谁想加一个
`{ kind: 'damageMul' }`，编译期就会在 `core` 与 `sim` 两侧同时报错，
因为两个 `computeDamage` 都会收到一个它们不认识的参数。

### 2.1.3 世界地图的界面（`ui/worldmap.ts`）

**三层渐进的 DOM 覆盖层**，与 `hud.ts` 同级，不碰 Three.js 场景：

```
第 1 层  世界地图   6 个场景节点，连线表示推荐顺序（不是强制顺序）
第 2 层  场景详情   该场景的子关卡列表 + 三档难度选择 + 签名维度标签
第 3 层  出击前确认 阵容编成（选 5 人）+ 该关的活跃维度提示
```

第 3 层的"维度提示"是**唯一一处把挑战维度直接告诉玩家的地方**。
不给的话玩家只能靠反复失败去猜，而本作的核心循环要求玩家
"看到维度 → 想到解法"——这个信息必须是明示的。

**当前数据层不做解锁限制**（任何场景任何关卡都能直接进），
`meta/unlock.ts` 先只提供查询接口，解锁曲线属于 M3。
这样做的原因是解锁规则还没定（`00-决策清单.md` E9），
先留下接口比先写死规则便宜。

### 2.1.4 两条成长线为什么在 `data/` 而不是 `meta/`（本轮新增）

`progression.ts` 放在 `data/` 而不是 `meta/`，因为它是**规则表，不是存档**：

| 在 `progression.ts`（纯数据） | 在 `Profile`（存档） |
|---|---|
| `starsFor` / `skillPointsFor` 通关·全员存活·任务 → 几星 → 给几点 | `stars` / `skillPoints` |
| `RANKS` / `TACTICS` 12 级军衔与战术动作 | `honor[heroId]` → `rankAt()` |
| `SHOP` 19 件装备与价格、`canEquip` | `owned` / `loadouts` |
| `HONOR_PER_TASK` / `HONOR_CLEAR_BONUS` | `honor` 他累计了多少 |
| `advancedSkillUnlocked(rank, purchased)` | —（纯函数，看上面两列求值） |

**同一条规则被 `sim/` 与 `core/` 两边引用，所以它只能在 `data/`。**
`04-技术框架.md` §1 的边界规定 `sim/` 与 `core/` 不互相 import——
把它们共享的东西放在 `data/` 是唯一不需要第三份实现的解法。

军衔的架构不变量也在这里执行（`00-决策清单.md` A27）：

```ts
export type RankEffect = Exclude<SpecEffect, { kind: 'attr' }>;
```

军衔**不能**给 `attr`，由编译器挡。`progression.ts` 底部还留了两个空常量
`RANK_GRANTED_ANSWERS` / `RANK_PRIMARY_DELTA` 作为运行时的第二道保险，
哨兵会断言它们为空——想给军衔加属性的人，会先撞上类型错误，再撞上哨兵断言。

### 2.2 三种阵型的数据形状（`characters.ts` 的 `SQUAD_COMMANDS`）

> **第三轮修订**：原来的四个命令按钮（自由 / 集火 / 重整阵型 / 紧密跟随）重构为
> **三个互斥阵型**。集火并入鼠标（见 §5.4），重整阵型并入"换档自动回位"（见 §5.6），
> 撤退并入"点队长身后"的移动意图（见 §5.4）。旧的 `kind: 'toggle' | 'action'`
> 与 `focusFire` 字段随之删除。

阵型仍然**不是**一套新的 AI 代码，但它也不再只是 `AIProfile` 的一层覆盖。
它管两件事：**站位锚点怎么算**，以及**切档时 `AIProfile` 覆盖什么**。
索敌 / 拴绳 / 走位 / 开火全部复用队员自己的 `aiProfile`——
阵型管的是"队伍长什么形状"，不管"队员怎么打架"。

```ts
interface FormationRing {
  roles: HeroRole[];   // 这一层站哪些定位（tank/meleeDps/rangedDps/control/support/summoner）
  radius: number;      // 锚点距队长的半径，格
  bearing: number;     // 相对阵型朝向的方位角：0 = 正前，π = 正后
  spread: number;      // 该层展开的总张角；2π = 铺满一圈（环形阵）
  tether: number;      // 最大活动半径，格。**硬约束**，超出即强制回位
}
interface SquadCommand {
  id: 'defend' | 'ring' | 'advance';
  name: string;
  facing: boolean;            // 吃不吃玩家指定的朝向。false = 环形，朝向无意义
  rings: FormationRing[];     // 从外到内排列
  overrides: Partial<AIProfile>;
}
```

| 阵型 | 朝向 | 近战层 | 远程层 | 中心层 | 覆盖了什么 |
|---|---|---|---|---|---|
| 普通防御 | 有 | r 2.2 / 前扇形 1.1π | r 4.4 / 后扇形 0.9π | r 1.3 | `{}` —— 默认态 |
| 环形防御 | 无 | r 3.0 / 铺满 2π | r 5.2 / 铺满 2π | r 1.6 | `engageDistanceMul: 0.9` |
| 搜索推进 | 有 | r 4.0 / 1.4π | r 5.5 / 1.2π | r 2.0 | `aggroRange: 6`、`engageDistanceMul: 1.15` |

**`rings` 的 `tether` 就是地面画出来的那个活动圈。** 可视化和硬约束读同一个字段，
不许有两份——否则玩家看到的圈和 AI 实际遵守的圈会随参数漂移，而这是最不该出错的地方。

**`HeroRole` 第一次被 AI 真正用上。** 它从第二轮就定义在 `characters.ts` 里，
但此前的阵型只用 `short()` 做了"近战 / 远程"二分，`support` / `control` / `summoner`
三个定位在 AI 里完全隐形。`FormationRing.roles` 让"辅助职业在中心位置"这类需求
落成数据，而不是又写一个分支。

**放在 `characters.ts` 而不是 `core/ai.ts`**：`AIProfile` 就在那个文件里，
`core/ai.ts` 的 M2 实现直接 import 这张表，不需要第三份数据结构。
与 §1 的边界一致——`data/` 是共享层，阵型表是**参数**，不是逻辑。

**默认档 `defend` 的 `overrides` 是 `{}`。** 这个比例本身就是设计约束
（`00-决策清单.md` A29）：阵型栏是**效率旋钮**，不是**操作门槛**。
压舱石仍是那句"**不碰阵型栏也能通关**"——所以默认值必须是"什么都不覆盖"。

> 三档**互斥**是同一条轴上的三个档位，不是三个独立开关。互斥不是限制，是**减负**：
> 旧的形态是两个独立二态开关（自由⇄集火、跟随⇄紧密跟随）加一个即时动作，
> 组合态需要玩家在脑子里同时维持两个位；三选一只需要维持一个位。
> 所以这一轮换的是**形状**，不是**数量**——`01-系统策划案.md` §5.3 那条
> "指令一多就变成 RTS"的担心，靠互斥档位继续守住。

### 2.3 障碍的通行位掩码（`TerrainTag` 的三个新值）

`core/terrain.ts` 不为每种障碍写一个分支，而是**每格存一个 4 位掩码**：

```
bit 0  BLOCK_MOVE      人不可通行
bit 1  BLOCK_SHOT      子弹被挡
bit 2  BLOCK_SIGHT     视线被挡
bit 3  DESTRUCTIBLE    可被打掉（打掉后该格掩码归零，留 residue）
```

| 障碍 | MOVE | SHOT | SIGHT | 可破坏 | 掩码 |
|---|---|---|---|---|---|
| 空地 | ✗ | ✗ | ✗ | — | `0` |
| 沙袋 / 铁丝网 | ✓ | ✗ | ✗ | ✓ | `1001` = 9 |
| 建筑（对照） | ✓ | ✓ | ✓ | ✗ | `0111` = 7 |
| 木墙 | ✓ | ✓ | ✓ | ✓ | `1111` = 15 |

**这张表就是"只引入两条新通行语义"在代码里的样子。**
`TerrainTag` 多了两个枚举值（`sandbag` / `wire` 共用同一个语义，
区分只在耐久 320 vs 180），但**掩码只多了一个值（9）**——
木墙不是第三种东西，它是建筑的值加上 `DESTRUCTIBLE` 位。

四个判定因此都退化成一次位与：

```
人能过吗      (mask & BLOCK_MOVE) === 0
子弹能过吗    (mask & BLOCK_SHOT) === 0
能看见吗      (mask & BLOCK_SIGHT) === 0
能被拆吗      (mask & DESTRUCTIBLE) !== 0
```

> **为什么挡视线要单独一位，而不是"挡子弹就等于挡视线"。**
> 两者在现有场景里恰好同进同出，看起来可以合并。但合并之后，
> "能穿烟/能看穿玻璃"这类东西以后再也加不进来——而合并省下的是一列数据，
> 不是一次判定（判定都是位与，多一位不多一条分支）。
> **结构上分开、数据上一致**，比合成一位便宜。

位掩码的来源是 `scenes.ts` 的 `OBSTACLES` 表，`core/terrain.ts` 只读它——
摆放在哪是 M2 的事，**语义是谁的由 `data/` 说了算**。

## 3. 主循环：固定步长逻辑 + 可变步长渲染

```
requestAnimationFrame
  ├─ 累积真实时间
  ├─ while (acc >= DT) { core.tick(DT); acc -= DT }      DT = 1/60
  └─ renderer.render(alpha)                              alpha = acc / DT
```

**为什么逻辑必须固定步长**：伤害结算、AI 决策、刷怪预算全是有状态的累加器。
可变步长会让同一个种子在不同帧率下跑出不同结果，模拟器与游戏再也对不上账。

**为什么渲染要插值**：俯视视角下，僵尸在 144Hz 显示器上如果只按 60Hz 更新位置，
会出现肉眼可见的抖动。渲染时用 `alpha` 在上一帧和当前帧的位置之间插值。
只需给位置和朝向各存一份 `prev`。

**帧预算（16.6ms 总额）**：

| 阶段 | 预算 | 说明 |
|---|---|---|
| core.tick × 1 | 6ms | 逻辑，含 AI + 寻路 + 碰撞 |
| 渲染提交 | 8ms | 剔除 + 实例更新 + draw call |
| 余量 | 2.6ms | 给 GC 和突发 |

6ms 够不够，取决于 §5 的寻路方案——那是唯一可能爆预算的东西。

## 4. 防止 `core/` 与 `sim/` 漂移：对账测试

两份伤害实现必然漂移，除非**强制它们对账**。

`tests/reconcile.test.ts` 做的事：给定同一组输入，
断言两边算出的伤害在 **1e-6** 内相等。

```ts
for (const hero of HEROES)
  for (const tier of [0, 1, 2])
    for (const level of [1, 3, 5])
      for (const target of [普通僵尸, 胖僵尸, 关底BOSS])
        assert.close(
          core.computeDamage(...) ,   // 游戏实现
          sim.computeDamage(...),     // 模拟器实现
          1e-6,
        )
```

组合数是 12 × 3 × 3 × 3 = 324 个用例。跑一次几毫秒。

**这条测试是整个技术框架里性价比最高的东西**：它让"改坏了数值公式"
在 1 秒内暴露，而不是等到真人试玩时发现伤害不对。
没有它，两份实现就是两颗定时炸弹。

## 5. 寻路：一个流场覆盖全场僵尸

### 5.1 为什么不用 A\*

N 只僵尸各跑一次 A\* 是经典错误。300 只僵尸 × 每次 A\* 展开几千格 = 每帧百万级操作，必然爆预算。

### 5.2 流场（Flow Field）方案

所有僵尸的目标是**同一个**——小队。所以只需要**一张**流场。

```
每 N 帧（或小队移动超过 1 格时）：
  从【小队所在格】做一次 BFS，展开半径上限 64 格
  每个格子存一个方向（指向父节点）→ 写进 Int32Array(256×256)
僵尸移动时：
  查自己所在格子的方向 → 朝那个方向走
```

**BFS 的展开半径限制是关键优化。** 不需要算满 256×256：

| 方案 | 展开格数 | 相对成本 |
|---|---|---|
| 全图 256² | 65,536 | 1.00x |
| **半径 64 格** | **≈ 12,900** | **0.20x** |
| 半径 25 格（=刷怪距离） | ≈ 1,960 | 0.03x |

半径 64 格已经比 `SPAWN_DISTANCE = 25` 富余一倍多——**僵尸在走进 25 格之前
就已经在流场里了**，不存在"没有方向可查"的情况。

半径之外的僵尸（被队伍甩下的落伍者）走**直线趋近**兜底，
等重新进入流场范围再接管。这条分支在实践中几乎不触发。

**每次 BFS 的真实成本**：12,900 格 × 每格 4 邻居比较 ≈ 5 万次操作，
JS 里约 **0.2-0.5ms**。按 4Hz 重算，摊到每帧是 **0.02ms**。

> 顺带一个美术收益：流场按固定频率重算，僵尸的路径会**滞后**于小队移动。
> 一秒钟前算的路径，对一群蹒跚的僵尸来说不是 bug，是想要的笨拙感。
> 想要更"聪明"的僵尸，提高重算频率即可——这是个手感旋钮，不是固定开销。

### 5.3 静态障碍

地形写进流场的**通行位图**。建筑格直接标记为不可通行，BFS 跳过。
所以"绕开建筑"是流场自带的，不需要额外处理。

流场只读上面 §2.3 掩码的 **`BLOCK_MOVE` 那一位**——沙袋和铁丝网因此也在流场里
算障碍（人过不去），但它们的 `BLOCK_SHOT = 0` 不进流场。
**流场是给移动用的，不是给弹道用的**，两者读同一个掩码的不同位。

水域需要按角色判断通行——但僵尸不能过水，所以对僵尸流场是障碍。
**能过水的角色是玩家那边的事**，走 A\*（见下），不影响流场。

### 5.4 鼠标控制队伍（第三轮：点击移动从"可选"升为主控制）

**左键单击地面 = 移动指令。** 落点即队伍新的中心，`SQUAD_COMMANDS` 那一档的
`rings` 立刻在落点周围算出每名队员的**目的站位锚点**，地面画出锚点与阵型朝向标识，
角色随后移动过去。

| 输入 | 行为 |
|---|---|
| 左键单击地面 | 移动指令。落点 = 队伍中心，阵型朝向**自动**决定（见 §5.5） |
| 左键按住拖拽 | 拖出箭头手动指定阵型朝向；松开后才落站位、才移动。仅对 `facing: true` 的档位有效 |
| 左键单击敌人 | 集火该目标（取代原来的"集火进攻"按钮） |
| **点队长身后** | **撤退**：保持原阵型与迎敌朝向，有序边打边撤 |
| 右键拖拽 | 相机 yaw（§7.4）。与左键完全分离，不冲突 |
| WASD | 微调平移，**不改变阵型**（见下） |

**"点队长身后"与"按住左键拖朝向"是两种意图，靠有没有拖拽区分。**
只点不拖、且落点在队长身后 → 判为撤退，队伍不转向，维持迎敌朝向往后走；
拖出箭头 → 判为指定朝向，队伍转到箭头方向。这两种意图在实现上是两条分支，
但共用同一套锚点计算与移动代码。

**集火并进鼠标**：原来是一个独立的二态按钮（`targetPriority: 'strongest'` + `focusFire`），
现在左键点敌人就是集火，再点地面解除。这样命令栏上不再有"集火"这一项，
`SquadCommand` 的 `focusFire` 字段随之删除（见 §2.2）。

**WASD 保留，但语义变了。** 不再是"五个队员各自朝输入方向走"，
而是**整队平移的微调**：`W` / `A` / `D` 按相机相对方向平移整个队伍，
**阵型朝向保持不变**（只挪位置，不转阵）；`S` 判为**撤退**，
和"点队长身后"走同一条分支——保持阵型与迎敌朝向边打边撤。

> 这是第三轮里唯一"看起来加了复杂度、实际减了复杂度"的地方：
> "按住 WASD 持续走"是连续输入，"点一下地面"是离散输入。
> 玩家从"手一直在动"变成"想好了点一下"，控制带宽是降的。

**落点校验**：点进 `BLOCK_MOVE` 格（建筑、沙袋）→ 吸附到最近的可走格，
与 §5.6 的锚点吸附复用同一个函数。不校验的话整队会朝一堵墙走到底。

### 5.5 阵型朝向：自动优先，玩家拖拽覆盖

有朝向的档位（普通防御、搜索推进）需要一个 yaw。**默认由系统决定，
玩家的左键拖拽是精调**——这样"不碰朝向也能通关"才成立。

**自动朝向用威胁扇区，不用"最近一只敌人"。** 把 360° 切成 8 个扇区，
数每个扇区里的敌人数，取最重的那个扇区的中心方向：

```
最重扇区 = argmax over 8 sectors of (该扇区敌人数 / (该扇区中心到队长的距离 + 1))
```

若用"朝向最近的那只敌人"，一只从侧面绕过来的僵尸就能骗走整队的朝向——
这是 bug 级的手感坑，且玩家无法理解为什么队伍突然转了个方向。

**环形的档位（`facing: false`）跳过这一步**：朝向对环形阵没有意义，
`rings` 里的 `spread = 2π` 已经让站位铺满一圈。

### 5.6 站位锚点：可达性吸附与卡住恢复

阵型每帧只改一件事——每个队员的**站位锚点**（原型里的 `h.home`）。
索敌 / 拴绳 / 走位 / 开火全部复用现成的队员 AI。这是原型里最值钱的结构，
第三轮沿用，不重写。

但原型有一处真实缺陷：**回位是直线走，撞墙就滑，卡住就永久卡住。**
如果锚点落在墙的另一侧，那名队员会一直贴着墙挪、永远到不了，
也不会有人发现——他就是慢慢掉队，最后单独战斗。这正好是
"不出现因为地形卡住丢失队员"要解决的问题。解法是两层，从便宜到贵：

**第一层：根因层——别把锚点指到墙里。** 锚点算完后做一次**可达性吸附**：
落在 `BLOCK_MOVE` 格就吸到最近的可走格。环形与扇形摆位踩到建筑是**必然**发生的
（"近战站左前方 3 格"，那里正好有栋楼），这一步消掉绝大部分卡死。

**第二层：兜底层——卡住检测。** 连续 N 帧位移低于阈值且未到位 → 判为卡住，
触发一次 `astar.ts` 算到锚点，缓存路径跟着走。**不是每帧算**，只有被卡时算一次，
99% 的时间里这条分支的成本是零。

**不给每名队员各配一张流场。** §5.2 那张流场能一张覆盖全场僵尸，
是因为**所有僵尸的目标相同**（小队）——而五名队员的锚点各不相同，共用不成立。
单次 `astar.ts` 调用就够，不需要新结构。

**回位优先于追击。** 接敌中的队员若锚点偏差超过该层的 `tether`，
**放弃当前目标先归位**。这条就是"近战不会被敌人带离"在代码里的样子——
`tether` 是硬约束，不是软牵引。地面画出来的活动圈读的也是这个字段，
所以玩家看到的圈和 AI 遵守的圈永远是同一个数。

---

### 5.7 队伍作为一个整体（第三轮的附带收益）

下面三条都不增加任何玩家操作，但直接命中"把队伍视作一个整体作战单元"。

**1. 移动途中不主动索敌。** 移动指令下达后，全队在到达锚点前不主动找架打，
只在被贴脸时自卫，到位才展开接敌。不加这条的话，跑在前面的队员先撞上僵尸就停下开火、
后面的还在走，**队伍被拉成一条长条**——这就是"某个队员单独战斗"的来源。

**2. 切档时按距离贪心分配槽位。** 现役的环形摆位是 `forEach((h, i) => ...)`
按固定索引给角度，**换档时可能全体对冲**（A 跑 B 的位、B 跑 A 的位，路上互相穿）。
改成"每名队员认领离自己最近的那个新槽位"，切阵型看起来才像**收缩**而不是打架。

**3. 环形阵按威胁动态分配角位。** 现役环阵是静态等分。只有两名近战时应该对分；
某一侧敌人特别多时应该往那侧多派人。这是环阵从静态摆位升级为动态摆位，
**且不增加任何玩家操作**。

## 6. 空间索引：给碰撞和索敌共用

僵尸之间要分离（避免叠在一起）、子弹要命中判定、AI 要索敌——
三者都需要"附近有哪些实体"。

**用统一网格哈希**（uniform grid hash），不是四叉树：

```
格子边长 = 2 × 最大僵尸半径 ≈ 2 格
每帧重建：300 次插入（数组 push）→ O(n)，不需要清空整个表
查询：3×3 邻域，常数时间
```

选网格哈希不选四叉树的原因：**实体每帧都在动**。
四叉树每帧重建的成本远高于网格哈希，而俯视射击的实体分布足够均匀，
网格哈希没有四叉树的退化问题。

## 7. 渲染

### 7.1 分块剔除

256×256 格分 8×8 = 64 个 chunk，每块 32×32 格。

俯视相机在典型缩放下的可视范围约 **40×40 格**，
即同时最多可见 **4 个 chunk**（跨边界时 6 个）。剔除掉 90% 以上的地块。

地形本身**烘焙成整块的合并 mesh**（每 chunk 一个），不是每格一个物体——
64 个 draw call 是上限，实际可见时只有 4-6 个。

### 7.2 InstancedMesh 池

| 对象 | 池大小 | 说明 |
|---|---|---|
| 僵尸（9 种各一个池） | 每类 120 | 一个池装不下 300 只，按类型分摊 |
| 子弹（可视化的） | 400 | 只有投掷物和火箭需要实体，其余走 hitscan |
| 血渍 / 弹坑 | 200 | 环形复用，不增长 |
| 增益道具 | 16 | |

**命中判定走 hitscan**（射线 vs 空间哈希），不做子弹实体——
14 把武器里只有手雷、火箭筒、回旋镖需要飞行实体。
其余 10 把用 hitscan，省掉一整个子弹更新循环。

### 7.3 阴影：只给小分队

真阴影贴图对 300 个移动单位太贵。方案：

- **定向光阴影**只覆盖相机中心 60×60 格，1024×1024 贴图，只渲染 5 名队员 + BOSS
- **僵尸用 blob shadow**（一个贴地的暗色圆片，跟着实例矩阵走，零额外 draw call）

俯视 3D 视角下，僵尸脚下那个圆片读起来和真阴影几乎没差别，
而队员是有细节的模型，值得真阴影。

### 7.4 相机

```
俯仰角：35° ~ 80°（下限防止穿地平线，上限防止变成纯正交）
旋转：  自由 yaw，鼠标右键拖拽
缩放：  滚轮，正交/透视混合 —— 远看接近正交（便于读战场），近看透视（有纵深）
```

**俯仰角下限 35° 是硬约束**：再低就会看到地图边缘外面，
而 256×256 的地图之外什么都没有。

## 8. 资产管线

```
角色 / 僵尸 / 武器：部件表 → tools/voxel.py（Blender）→ GLB（顶点色，无贴图）→ gltf-transform meshopt → assets/
地形道具：        Rodin 生成或手拼 → 体素化 → 同上
```

命令（一次性，写进 `package.json` 的 script）：

```
gltf-transform optimize in.glb out.glb --compress draco --texture-compress ktx2
```

美术是 Q 版体素（`00` A3）：每个部件整块绑一根骨，不做权重。旧路线的背景：见 `05-资产清单.md` §1
对"哪些用 Rodin、哪些买"的划分。

## 9. TypeScript / 构建配置

```
Node 24 原生 type stripping（≥23.6）→ node xxx.ts 直接跑，无需 tsx/ts-node
  · 所有 import 必须带显式 .ts 后缀
  · 因此 tsconfig 需要 allowImportingTsExtensions + noEmit
```

这份配置**同时服务于 `sim/`（node 直接跑）和 Vite（游戏构建）**——
一份 tsconfig，两边都能用，不需要为模拟器单独留一套。

**Vite 只负责游戏**，`sim/` 不进打包产物。`package.json` 里两条独立命令：

```
npm run sim     →  node src/sim/balance-check.ts      （数值哨兵）
npm run dev     →  vite                                （游戏）
```

## 10. 这条路线上的三个风险

| 风险 | 触发条件 | 应对 |
|---|---|---|
| 流场重算频率不够 | 僵尸在拐角处贴墙抖动 | 提高重算频率；给流场方向加一点随机扰动，让它们"贴墙滑"而不是"卡墙" |
| 队员 AI 可读性差 | 5 个人各打各的，玩家看不懂 | 见 `00-决策清单.md` E1——这是原型阶段第一优先验证项 |
| 两份伤害实现漂移 | 有人改了 `sim/combat.ts` 没改 `core/` | §4 的对账测试。**这条必须在 M1 就建起来**，不能等到 M3 |

第三条是最容易被推迟、也最贵的一条。**对账测试要和对账对象同时诞生。**
