# 04 技术框架

> 这一版框架不是从零设计的，是**从已经跑通的代码里长出来的**。
> `src/data/` + `src/sim/` 这套"数值真源 + 无渲染哨兵"的结构已经在用，
> 本文要做的是把它扩成一个能跑的游戏，而不是换一套新架构。

---

## 1. 最重要的一条架构决定：模拟器**不**升级成引擎

最省事的做法是"把 `src/sim/` 加个渲染层，直接变成游戏"。
**不这么做**，理由是它已经在 §10 被实测证伪过一次：

| 模拟器简化 | 变成引擎时必须做的事 |
|---|---|
| 一维距离 | 二维空间 + 寻路 + 包围 |
| 单点索敌 | 多目标 + 空间分区 |
| 队员不走位 | 走位、牵引、地形回避 |

要让 `sim/` 撑起这些，它就得引入寻路、空间索引、地形——
而这些恰恰是它**现在能跑得比游戏快 1000 倍**的原因。
把哨兵改造成引擎，等于同时失去哨兵和引擎。

**边界定在这里：**

```
src/data/   ← 唯一共享层。策划案、模拟器、游戏三者共用的数值真源
src/sim/    ← 只给平衡用。无渲染、无寻路、批量化。永远不 import three
src/core/   ← 游戏逻辑。无渲染，但【有】二维空间、寻路、地形
src/game/   ← Three.js 渲染。只读 core 的状态，不改
src/ui/     ← DOM 覆盖层（HUD / 结算 / 小队面板）
```

`sim/` 和 `core/` **不互相 import**。它们各自 import `data/`。
这样"改了数值表，模拟器读数和游戏行为一起变"，但两边的实现可以完全不同。

> **代价**：同一套伤害公式会有两份实现（`sim/combat.ts` 和 `core/`）。
> 这是刻意的取舍——共享公式会逼着两边互相迁就，
> 而它们要回答的问题本来就不一样（"数值自洽吗" vs "打起来什么样"）。
> 防漂移的手段不是共享代码，是 §4 的**对账测试**。

## 2.1 元层：`meta/` 为什么单独存在（本轮新增）

长期成长线（解锁关卡 → 换阵容 → 通关下一关）需要**跨局持久化**的状态。
它不能放进 `core/`——`core/` 是"一局之内"的世界状态，随 run 结束销毁；
也不该放进 `ui/`——存档是逻辑，不是界面。

所以新开一层 `meta/`，与 `core/` `sim/` 同级，同样**禁止 import `three`**
（同一个 ESLint 规则覆盖），并且**只 import `data/`**。

```
meta/profile.ts   →  import { SCENES, SCENE_BY_ID, expandScene } from '../data/scenes.ts'
                  →  import { HEROES, WEAPONS } from '../data/characters.ts'
                  ✗  绝不 import core/ game/ ui/
```

**依赖方向是单向的**：`data/` ← `meta/` ← `ui/`。
`core/` 不认识 `meta/`——一局怎么打，与"这个玩家解锁了什么"无关。
衔接点在 `game/main.ts`：读 `meta` 决定加载哪个子关卡，把
`expandScene(scene, difficulty)` 的结果**当成参数**交给 `core/`。

### 2.1.1 存档 schema

```ts
type Profile = {
  version: 1;                          // ★ 必须有，否则改结构时老存档无法迁移
  cleared: string[];                   // 已通关的子关卡 id（'jungle-07'），82 关的进度真源
  unlockedHeroes: string[];            // 角色 id
  unlockedWeapons: string[];           // 武器【种类】，按 C3 不含数值
  specPoints: number;                  // 未分配的专精点
  specs: Record<string, string[]>;     // 角色 id → 已点开的节点 id
};
```

三条规则：

1. **`cleared` 存关卡 id，不存"进度百分比"。** 关卡 id 由 `scenes.ts` 推导，
   是稳定的；百分比会在关数变化时失准（本轮就动过 15 → 13）。
2. **`unlockedWeapons` 存种类，不存阶。** 按 C3 武器不做局外养成——
   武器阶 0→2 全靠局内金钱（`run.ts` 的 `LEVEL_COST`），存档里没有它的位置。
3. **`specs` 存节点 id，不存效果。** 效果从 `characters.ts` 的
   `specialization` 现算——否则改一次节点数值就要迁移全部存档。

存档落地方式由 M3 决定（`localStorage` 或文件），本节只钉 schema。

### 2.1.2 为什么专精不能进伤害公式（这条约束是编译器执行的）

`meta/` 会往 `core/` 传一个角色列表。很自然的想法是"顺便把专精效果也传进去"——
**不能。** 原因在 §4 的对账测试。

```
core.computeDamage(...)   与   sim.computeDamage(...)   签名必须完全一致
                          ↑
      前提是：伤害只由「属性 / 等级 / 武器阶 / 技能参数 / 目标护甲」决定
```

专精的效果被**限定在公式的输入侧**：

```ts
export type SpecEffect =
  | { kind: 'attr'; ... }        // 改属性   → 改了公式的输入
  | { kind: 'weaponTier'; ... }  // 改武器阶 → 同上
  | { kind: 'skill'; ... }       // 改技能参数 → 同上
  | { kind: 'ai'; ... }          // 改 AI 参数 → 不进公式
  | { kind: 'answer'; ... }      // 加维度答案 → 不进公式
  | { kind: 'revive'; ... };     // 复活次数 → 不进公式
```

**里面刻意没有"新增伤害乘区"这个变体。** 所以专精满点的角色对 `computeDamage`
而言，就是一个"属性更高、武器阶更高、技能参数不同"的普通角色——
签名没变，对账测试继续成立。

**这条由 TypeScript 联合类型执行，不是靠注释提醒。** 谁想加一个
`{ kind: 'damageMul' }`，编译期就会在 `core` 与 `sim` 两侧同时报错，
因为两个 `computeDamage` 都会收到一个它们不认识的参数。

### 2.1.3 世界地图的界面（`ui/worldmap.ts`）

**三层渐进的 DOM 覆盖层**，与 `hud.ts` 同级，不碰 Three.js 场景：

```
第 1 层  世界地图   6 个场景节点，连线表示推荐顺序（不是强制顺序）
第 2 层  场景详情   该场景的子关卡列表 + 三档难度选择 + 签名维度标签
第 3 层  出击前确认 阵容编成（选 5 人）+ 该关的活跃维度提示
```

第 3 层的"维度提示"是**唯一一处把挑战维度直接告诉玩家的地方**。
不给的话玩家只能靠反复失败去猜，而本作的核心循环要求玩家
"看到维度 → 想到解法"——这个信息必须是明示的。

**当前数据层不做解锁限制**（任何场景任何关卡都能直接进），
`meta/unlock.ts` 先只提供查询接口，解锁曲线属于 M3。
这样做的原因是解锁规则还没定（`00-决策清单.md` E9），
先留下接口比先写死规则便宜。

## 3. 主循环：固定步长逻辑 + 可变步长渲染

```
requestAnimationFrame
  ├─ 累积真实时间
  ├─ while (acc >= DT) { core.tick(DT); acc -= DT }      DT = 1/60
  └─ renderer.render(alpha)                              alpha = acc / DT
```

**为什么逻辑必须固定步长**：伤害结算、AI 决策、刷怪预算全是有状态的累加器。
可变步长会让同一个种子在不同帧率下跑出不同结果，模拟器与游戏再也对不上账。

**为什么渲染要插值**：俯视视角下，僵尸在 144Hz 显示器上如果只按 60Hz 更新位置，
会出现肉眼可见的抖动。渲染时用 `alpha` 在上一帧和当前帧的位置之间插值。
只需给位置和朝向各存一份 `prev`。

**帧预算（16.6ms 总额）**：

| 阶段 | 预算 | 说明 |
|---|---|---|
| core.tick × 1 | 6ms | 逻辑，含 AI + 寻路 + 碰撞 |
| 渲染提交 | 8ms | 剔除 + 实例更新 + draw call |
| 余量 | 2.6ms | 给 GC 和突发 |

6ms 够不够，取决于 §5 的寻路方案——那是唯一可能爆预算的东西。

## 4. 防止 `core/` 与 `sim/` 漂移：对账测试

两份伤害实现必然漂移，除非**强制它们对账**。

`tests/reconcile.test.ts` 做的事：给定同一组输入，
断言两边算出的伤害在 **1e-6** 内相等。

```ts
for (const hero of HEROES)
  for (const tier of [0, 1, 2])
    for (const level of [1, 3, 5])
      for (const target of [普通僵尸, 胖僵尸, 关底BOSS])
        assert.close(
          core.computeDamage(...) ,   // 游戏实现
          sim.computeDamage(...),     // 模拟器实现
          1e-6,
        )
```

组合数是 12 × 3 × 3 × 3 = 324 个用例。跑一次几毫秒。

**这条测试是整个技术框架里性价比最高的东西**：它让"改坏了数值公式"
在 1 秒内暴露，而不是等到真人试玩时发现伤害不对。
没有它，两份实现就是两颗定时炸弹。

## 5. 寻路：一个流场覆盖全场僵尸

### 5.1 为什么不用 A\*

N 只僵尸各跑一次 A\* 是经典错误。300 只僵尸 × 每次 A\* 展开几千格 = 每帧百万级操作，必然爆预算。

### 5.2 流场（Flow Field）方案

所有僵尸的目标是**同一个**——小队。所以只需要**一张**流场。

```
每 N 帧（或小队移动超过 1 格时）：
  从【小队所在格】做一次 BFS，展开半径上限 64 格
  每个格子存一个方向（指向父节点）→ 写进 Int32Array(256×256)
僵尸移动时：
  查自己所在格子的方向 → 朝那个方向走
```

**BFS 的展开半径限制是关键优化。** 不需要算满 256×256：

| 方案 | 展开格数 | 相对成本 |
|---|---|---|
| 全图 256² | 65,536 | 1.00x |
| **半径 64 格** | **≈ 12,900** | **0.20x** |
| 半径 25 格（=刷怪距离） | ≈ 1,960 | 0.03x |

半径 64 格已经比 `SPAWN_DISTANCE = 25` 富余一倍多——**僵尸在走进 25 格之前
就已经在流场里了**，不存在"没有方向可查"的情况。

半径之外的僵尸（被队伍甩下的落伍者）走**直线趋近**兜底，
等重新进入流场范围再接管。这条分支在实践中几乎不触发。

**每次 BFS 的真实成本**：12,900 格 × 每格 4 邻居比较 ≈ 5 万次操作，
JS 里约 **0.2-0.5ms**。按 4Hz 重算，摊到每帧是 **0.02ms**。

> 顺带一个美术收益：流场按固定频率重算，僵尸的路径会**滞后**于小队移动。
> 一秒钟前算的路径，对一群蹒跚的僵尸来说不是 bug，是想要的笨拙感。
> 想要更"聪明"的僵尸，提高重算频率即可——这是个手感旋钮，不是固定开销。

### 5.3 静态障碍

地形写进流场的**通行位图**。建筑格直接标记为不可通行，BFS 跳过。
所以"绕开建筑"是流场自带的，不需要额外处理。

水域需要按角色判断通行——但僵尸不能过水，所以对僵尸流场是障碍。
**能过水的角色是玩家那边的事**，走 A\*（见下），不影响流场。

### 5.4 队长点地寻路

只有队长需要 A\*（玩家点击地面时算一次，不是每帧）。
256×256 网格 A\*，单次最坏几万次操作，点一下算一次，可以忽略不计。

> 键盘走位（WASD）不需要寻路——直接朝输入方向移动，撞墙就滑动。
> A\* 只服务于"点击移动"这个可选操作。

## 6. 空间索引：给碰撞和索敌共用

僵尸之间要分离（避免叠在一起）、子弹要命中判定、AI 要索敌——
三者都需要"附近有哪些实体"。

**用统一网格哈希**（uniform grid hash），不是四叉树：

```
格子边长 = 2 × 最大僵尸半径 ≈ 2 格
每帧重建：300 次插入（数组 push）→ O(n)，不需要清空整个表
查询：3×3 邻域，常数时间
```

选网格哈希不选四叉树的原因：**实体每帧都在动**。
四叉树每帧重建的成本远高于网格哈希，而俯视射击的实体分布足够均匀，
网格哈希没有四叉树的退化问题。

## 7. 渲染

### 7.1 分块剔除

256×256 格分 8×8 = 64 个 chunk，每块 32×32 格。

俯视相机在典型缩放下的可视范围约 **40×40 格**，
即同时最多可见 **4 个 chunk**（跨边界时 6 个）。剔除掉 90% 以上的地块。

地形本身**烘焙成整块的合并 mesh**（每 chunk 一个），不是每格一个物体——
64 个 draw call 是上限，实际可见时只有 4-6 个。

### 7.2 InstancedMesh 池

| 对象 | 池大小 | 说明 |
|---|---|---|
| 僵尸（9 种各一个池） | 每类 120 | 一个池装不下 300 只，按类型分摊 |
| 子弹（可视化的） | 400 | 只有投掷物和火箭需要实体，其余走 hitscan |
| 血渍 / 弹坑 | 200 | 环形复用，不增长 |
| 增益道具 | 16 | |

**命中判定走 hitscan**（射线 vs 空间哈希），不做子弹实体——
13 把武器里只有手雷、火箭筒、回旋镖需要飞行实体。
其余 10 把用 hitscan，省掉一整个子弹更新循环。

### 7.3 阴影：只给小分队

真阴影贴图对 300 个移动单位太贵。方案：

- **定向光阴影**只覆盖相机中心 60×60 格，1024×1024 贴图，只渲染 5 名队员 + BOSS
- **僵尸用 blob shadow**（一个贴地的暗色圆片，跟着实例矩阵走，零额外 draw call）

俯视 3D 视角下，僵尸脚下那个圆片读起来和真阴影几乎没差别，
而队员是有细节的模型，值得真阴影。

### 7.4 相机

```
俯仰角：35° ~ 80°（下限防止穿地平线，上限防止变成纯正交）
旋转：  自由 yaw，鼠标右键拖拽
缩放：  滚轮，正交/透视混合 —— 远看接近正交（便于读战场），近看透视（有纵深）
```

**俯仰角下限 35° 是硬约束**：再低就会看到地图边缘外面，
而 256×256 的地图之外什么都没有。

## 8. 资产管线

```
Rodin 生成 → GLB → gltf-transform → Draco 压缩 + KTX2 贴图 → assets/
```

命令（一次性，写进 `package.json` 的 script）：

```
gltf-transform optimize in.glb out.glb --compress draco --texture-compress ktx2
```

**一条必须先知道的事实**：Rodin 产出的是**静态网格**，不带骨骼动画。见 `05-资产清单.md` §1
对"哪些用 Rodin、哪些买"的划分。

## 9. TypeScript / 构建配置

```
Node 24 原生 type stripping（≥23.6）→ node xxx.ts 直接跑，无需 tsx/ts-node
  · 所有 import 必须带显式 .ts 后缀
  · 因此 tsconfig 需要 allowImportingTsExtensions + noEmit
```

这份配置**同时服务于 `sim/`（node 直接跑）和 Vite（游戏构建）**——
一份 tsconfig，两边都能用，不需要为模拟器单独留一套。

**Vite 只负责游戏**，`sim/` 不进打包产物。`package.json` 里两条独立命令：

```
npm run sim     →  node src/sim/balance-check.ts      （数值哨兵）
npm run dev     →  vite                                （游戏）
```

## 10. 这条路线上的三个风险

| 风险 | 触发条件 | 应对 |
|---|---|---|
| 流场重算频率不够 | 僵尸在拐角处贴墙抖动 | 提高重算频率；给流场方向加一点随机扰动，让它们"贴墙滑"而不是"卡墙" |
| 队员 AI 可读性差 | 5 个人各打各的，玩家看不懂 | 见 `00-决策清单.md` E1——这是原型阶段第一优先验证项 |
| 两份伤害实现漂移 | 有人改了 `sim/combat.ts` 没改 `core/` | §4 的对账测试。**这条必须在 M1 就建起来**，不能等到 M3 |

第三条是最容易被推迟、也最贵的一条。**对账测试要和对账对象同时诞生。**
