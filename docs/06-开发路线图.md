# 06 开发路线图

> 拆成 6 个里程碑，每个都有**可执行的验收标准**——不是"完成 XX 功能"，
> 是"跑 XX 命令得到 XX 结果"。
>
> 排序原则：**先做会推翻后面所有工作的那件事。**
> 所以 M0 是资产可行性验证，M1 是对账测试——它们都不产出玩家能看见的东西，
> 但它们是唯一两个"做错了要重来"的关卡。

---

## 总览

| 里程碑 | 目标 | 主要风险 | 能不能跳过 |
|---|---|---|---|
| **M0** | 资产可行性验证 | 动画方案不成立 → 换美术路线 | ❌ 不能 |
| **M1** | `core/` 逻辑骨架 + 对账测试 | 两份伤害实现漂移 | ❌ 不能 |
| **M2** | 渲染与操控（可玩原型） | 同屏 300 僵尸性能 | ❌ 不能 |
| **M3** | 完整关卡循环 | 15 分钟体感 | 可延后 |
| **M4** | 内容铺满（12 角色 / 6 地图） | 内容量 | 可延后 |
| **M5** | 打磨与发布准备 | — | 最后做 |

**M0 和 M1 是不可跳过的。** 其余都可以按需要裁剪。

---

## M0 — 资产可行性验证

**唯一的产出是一个能动的模型。** 不写游戏代码。

### 要回答的问题

`05-资产清单.md` §1.1 提出的方案是"Rodin 生成外观 + 现成骨架重定向"。
**这条路没验证过，而它决定整个美术路线。**

### 任务

1. 用 §2.2 的模板生成 1 个角色（建议先做鹰眼·薇拉）
2. 买/找一个带动画的 low-poly 人形包（含 idle / move / attack / death）
3. 把生成的网格绑到买来的骨架上，做权重
4. 导出 GLB，在 Three.js 里播放一段动画

### 验收标准

```
□ 生成的角色能在浏览器里播放 idle 动画
□ 动画播放时网格没有明显撕裂（权重正常）
□ 单个角色 GLB（Draco + KTX2）< 1.5 MB
□ 渲染 5 个角色实例，GPU 帧时间 < 2ms
```

**如果第 1、2 条不成立** → 重定向方案失败，退回"全部买现成包 + 换材质区分"。
这个决定必须在写任何游戏代码之前做完。

### 顺带要验证的

- Rodin 生成的网格**面数**是否在可接受范围（建议目标 < 8k 三角面/角色）
- 生成的贴图分辨率（俯视视角下 1024² 完全够，2048² 是浪费）

## M1 — `core/` 逻辑骨架 + 对账测试

**产出：一个没有画面的、能跑完 15 分钟关卡的逻辑核心。**

### 任务

```
src/core/world.ts      世界状态：实体数组 + 网格哈希
src/core/tick.ts       固定步长主循环
src/core/combat.ts     伤害结算（与 sim/combat.ts 对账）
src/core/spawn.ts      威胁预算刷怪（直接读 run.ts 的 STAGES）
src/core/ai.ts         队员 AI 三层
src/core/squad.ts      队长控制 + 软硬牵引
tests/reconcile.test.ts ★
```

**寻路先不做**（M2 再加）。M1 里用"直线趋近"临时替代——
因为 M1 要验证的是**公式**，不是**空间**。

### 验收标准

```
□ node tests/reconcile.test.ts
  → 324 个用例全部在 1e-6 内相等，0 失败

□ node src/core/headless-run.ts
  → 能跑完 15 分钟，输出：击杀数 / 通关与否 / 三个 BOSS 的击杀秒数
  → 这三个数字与 sim 的读数【接近但不相同】（差异来自二维空间，符合预期）
```

### 关于"接近但不相同"

**M1 的验收不是"core 和 sim 跑出一样的结果"**，那是错的期待。
它们用的是不同的空间模型，结果必然不同。

要验收的是：**completion 级别的结论一致**——
sim 说"通关"，core 也该通关；sim 说"BOSS 3 用了 53 秒"，core 该在 40-70 秒之间。

如果 core 跑出来 BOSS 3 要 200 秒，那说明**二维空间让输出大幅度稀释了**，
这是个真实的设计发现，该回头改数值，而不是改 core 去迁就 sim。

> 这正是 `02-数值表.md` §10 说的那条边界的延续：
> sim 回答"自洽"，core 第一次能回答"在这套空间模型下还成不成立"。

## M2 — 渲染与操控（可玩原型）

**产出：能玩的东西。** 这是第一个能交给别人试玩的版本。

### 任务

```
src/core/path/flowfield.ts    流场寻路
src/core/path/astar.ts        队长点地寻路
src/core/terrain.ts           地形与通行性
src/game/main.ts              bootstrap
src/game/camera.ts            俯视可旋转相机
src/game/renderer/chunks.ts   分块剔除
src/game/renderer/instances.ts InstancedMesh 池
src/game/input.ts             WASD + 鼠标
src/ui/hud.ts  squadbar.ts
```

**只做 1 张地图**（建议城市——建筑能验证流场绕障）。

### 验收标准

```
□ 同屏 300 只僵尸 @ 60fps（桌面端 GTX 1660 级别）
  → 用调试面板手动刷 300 只，跑 60 秒，帧时间 P99 < 16.6ms

□ core.tick() 单帧 < 6ms（含 300 僵尸的 AI + 流场查询）

□ 相机可以：鼠标右键旋转 / 滚轮缩放 / 俯仰角限制在 35°-80°

□ WASD 移动队长，4 名队员跟随且不穿墙

□ Tab 切换队长，整队重心正确移动

□ 僵尸能绕开建筑走到小队身边（流场生效，不是贴墙抖）
```

### 这个里程碑结束时必须做的第一件事

**找人试玩 10 分钟，专门验证 `00-决策清单.md` E1**：
> 玩家能否在混乱中看懂"谁在打谁"？

这是整个设计里最高风险的一条假设——**如果读不懂，游戏就不成立**，
而它没法靠数值或代码解决，只能靠 UI 和 AI 参数调。

## M3 — 完整关卡循环

**产出：一局完整的 15 分钟，含三个 BOSS、六张地图之一、结算。**

### 任务

```
src/core/boss.ts          BOSS 行为（含毒母的召唤、卡俄斯的混合刷新）
src/core/buff.ts          增益道具生成与拾取
src/core/quest.ts         任务 NPC（三种类型）
src/ui/result.ts          结算界面
六张地图的地形数据          （资产复用 §5 的方案）
```

### 验收标准

```
□ 完整跑完一局 15 分钟，中途无崩溃、无卡死
□ 三个 BOSS 都能击杀，超时能正确判负
□ 五个增益道具都能拾取并生效
□ 队员死亡后永久损失，直到本局结束
□ 六张地图都能加载，地形机制都生效（水/沼泽/冰面/可破坏）
□ 结算界面正确显示：通关与否、击杀数、阵亡名单、用时
```

### 这个里程碑要回答的核心问题

**15 分钟是不是太长？**（`00-决策清单.md` C1）

C1 的结论是"保留 15 分钟，但留给试玩判断"。M3 是唯一能真正回答它的地方——
看试玩的人在第 12 分钟时是在战斗，还是在等结算。

**如果是在等结算**，动作是**降低 `LEVEL_COST`**（让成长更快），
而不是砍时长。理由写在 C1 里。

## M4 — 内容铺满

**产出：全部 12 个角色、6 张地图、13 把武器都能实际使用。**

### 任务

- 12 个角色的模型 + 动画接入（M0 验证过的管线批量跑）
- 7 种僵尸 + 3 个 BOSS 的模型接入
- 6 张地图的地表贴图与专属资产
- 角色选择界面、武器升级界面

### 验收标准

```
□ 12 个角色全部可用，视觉上一眼能分辨（对着 §2.1 的表逐条核对）
□ 7 种僵尸在 300 只同屏时仍然能分辨类型（这是行为可读性的底线）
□ 6 张地图的地形机制全部生效
□ 每把武器升到 +2 阶的外观/特效有变化
```

### 这里有一条容易被忽略的验收项

**7 种僵尸在 300 只同屏时仍然能分辨**——
单个模型好看不代表挤在一起还能读。
`05-资产清单.md` §3 强调"轮廓 > 细节"就是为这一条服务的。

## M5 — 打磨与发布准备

**产出：可以发布的东西。**

| 项 | 说明 |
|---|---|
| 音效接入 | 按 `05-资产清单.md` §7 的优先级，先做"必须听见的" |
| 画面设置 | 质量档位、僵尸数量上限（照顾低端机） |
| 存档 | 局外解锁进度（只存解锁，不存数值——见 C3） |
| 难度档 | 两档，只改 `threatRateStart/End`，不改僵尸血量（见 C4） |
| 教程 | 只需要教三件事：WASD、Tab 换队长、集火 |
| 打包 | 桌面端 / Web 二选一 |

**教程只教三件事**——这本身就是设计的自检：
如果需要教第四件事，说明操作复杂度失控了。

## 关键路径

```
M0 ──→ M1 ──→ M2 ──→ M3 ──→ M4 ──→ M5
 │      │      │
 │      │      └─ 第一个能试玩的版本（也是第一次能验证 E1）
 │      └─ 对账测试建立（此后所有数值改动都有安全网）
 └─ 美术路线的生死判定
```

**M0 → M1 是可以并行的**：M0 验证美术时，M1 的逻辑骨架不依赖任何美术。
如果人手够，这两条同时开始，M2 汇合。

---

## 每完成一个里程碑要重跑的东西

```
node src/sim/balance-check.ts     数值哨兵，确认配平没被改动破坏
node tests/reconcile.test.ts      core 与 sim 的公式没漂移
```

**这两条命令要进 CI**（哪怕只是一个 pre-commit hook）。
它们的全部价值就在于"跑得够快，所以每次都会跑"——
一旦变成"改动大了才跑"，就等于没有。

## 现在处在哪一步

```
✅ 创意阶段规划（docs/00-06）
✅ 数值核心与模拟器（src/data + src/sim）—— 配平已闭环
⬜ M0 资产可行性验证        ← 下一步
⬜ M1 core 逻辑骨架
```

**下一步该做的是 M0，不是 M1。** 尽管 M1 看起来更"像写游戏"。

理由：M0 可能推翻美术路线，而美术路线会影响 M1 之后所有资源相关的接口设计。
先做会推翻后面工作的事。
