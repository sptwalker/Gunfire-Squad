# 06 开发路线图

> 拆成 7 个里程碑，每个都有**可执行的验收标准**——不是"完成 XX 功能"，
> 是"跑 XX 命令得到 XX 结果"。
>
> 排序原则：**先做会推翻后面所有工作的那件事。**
> 所以 M0 是资产可行性验证，M1 是对账测试——它们都不产出玩家能看见的东西，
> 但它们是唯一两个"做错了要重来"的关卡。

## M0 — 资产可行性验证 ✅

**唯一的产出是一个能动的模型。** 不写游戏代码。

> **已完成（2026-09-29）**。结论：**"Rodin 生成外观 + 现成骨架驱动"成立，武器可换成立**，
> 美术路线不用退。实测数字与剩下的坑见本节末尾的「M0 实测」。

### 要回答的问题

`05-资产清单.md` §1.1 提出的方案是"Rodin 生成外观 + 现成骨架重定向"。
**这条路没验证过，而它决定整个美术路线。**

### 任务

1. 用 §2.2 的模板生成 1 个角色（建议先做鹰眼·薇拉），**空手**（`05` §2.3）
2. 买/找一个带动画的 low-poly 人形包（含 idle / move / hit / death + 至少"双手射击""单手近战"两种攻击）
3. 把生成的网格绑到买来的骨架上，做权重；在右手加 `socket_hand_r`
4. 生成 2 把武器：狙击枪（双手射击）+ 剑（单手近战），原点放在握把
5. 导出 GLB，在 Three.js 里播放动画，运行时把武器挂到 `socket_hand_r`，按键切换武器与对应攻击动画

### 验收标准

```
□ 生成的角色能在浏览器里播放 idle 动画
□ 动画播放时网格没有明显撕裂（权重正常）
□ 单个角色 GLB（Draco + KTX2）< 1.5 MB
□ 渲染 5 个角色实例，GPU 帧时间 < 2ms
□ 运行时换武器：模型挂上手、朝向正确，不用逐把手调偏移
□ 换武器后攻击动画随握持切换，idle / move / hit / death 不受影响
□ 单把武器 GLB < 200 KB
```

**如果换武器那两条不成立** → 退回"武器烘进角色网格"，军械库只换数值不换外观
（裁决 #1 的"共享"在视觉上会打折扣，要回头找用户确认）。

**如果第 1、2 条不成立** → 重定向方案失败，退回"全部买现成包 + 换材质区分"。
这个决定必须在写任何游戏代码之前做完。

### 顺带要验证的

- Rodin 生成的网格**面数**是否在可接受范围（建议目标 < 8k 三角面/角色）
- 生成的贴图分辨率（俯视视角下 1024² 完全够，2048² 是浪费）

### M0 实测

产物在 `proto/m0/`：`index.html` 是验证台（仓库根目录 `python -m http.server`，打开 `/proto/m0/`），
`tools/accept.py` 一条命令重跑全部截图与 GPU 计时。

```
✅ 生成的角色能在浏览器里播放 idle 动画          idle / run / walk / hit / death / 2 种攻击 / 持刀，共 8 条
✅ 动画播放时网格没有明显撕裂                    修过三轮，见下方"第一轮验收为什么漏了"
✅ 单个角色 GLB < 1.5 MB                         559 KB（4,832 顶点 / 抽面目标 7,800 三角面，贴图 1024² WebP）
✅ 渲染 5 个角色实例，GPU 帧时间 < 2ms           0.09 ms（RTX 5080 / ANGLE D3D11，5 实例 + 武器约 58k 三角面）
✅ 运行时换武器：挂上手、朝向正确、不逐把调偏移   两把武器共用一个常量 Rx(-90°)，零逐把偏移
✅ 换武器后攻击动画随握持切换                    1 = 狙击枪 + attack_rifle，2 = 剑 + attack_melee1h
✅ 单把武器 GLB < 200 KB                         狙击枪 54 KB · 剑 38 KB
```

**第一轮验收为什么漏了**：第一轮只看了 5 个实例的远景和俯视截图，用户近看发现站立就破面、
右腿过粗、手部乱、跑步撕衣服、剑挂在剑尖上、枪过大。根因与修法：

| 现象 | 根因 | 修法 |
|---|---|---|
| 站立就破面、袖子拉成尖刺 | 把 A-pose 网格"反蒙皮"回 T-pose，线性蒙皮的逆在远离骨骼的衣服上不成立 | **网格不动，把拟合出的 A-pose 应用成骨架的静止姿态**；Xbot 动作在世界空间逐骨复制、烘焙到新静止姿态 |
| 右腿过粗、抬手拉出长刺 | Rodin 把垂着的手和大腿长成一块，同一批顶点既跟手又跟腿 | 手臂 / 腿臀按权重二选一；前臂·手与腿之间的粘连面直接删掉（86 面） |
| 跑步时两腿间拉膜 | 裆下顶点借了对侧腿的权重 | 裆下按左右砍掉对侧腿权重 |
| 长风衣下摆被腿撕开 | 过膝下摆离腿远，任何权重都不对 | **重新生成为短夹克**（v6），不再修风衣 |
| 夹克袖子贴图错、破面；挥砍 / 死亡时袖子粘在腰上 | v6 的手臂贴着衣身生成，袖子内侧和腰侧是同一片网格 | **重新生成为连体服**（v8，手臂离身、手指并拢、戴手套）；手臂与腿臀之间的面整段切开，袖子内侧拿到臀部权重的改投手臂权重 |
| 脸糊 | Rodin 纯文字生成的脸随机 | v7 抽到一张清楚的脸 → 左右镜像成对称参考图 → v8 用参考图 + 文字生成 |
| 手乱、握不住 | Rodin 的手套手指和 Xbot 指骨对不上，逐指分权重一弯就撕 | **手按刚体处理**（整只归 Hand 骨）；端枪时左手用两骨 IK 托到护木上 |
| 持刀跑刀尖朝下 | 跑步动作的右臂在甩 | 运行时合成 `run_melee1h`：只把右臂钉在持刀姿态（刀尖朝前上），左臂照常摆 |
| 剑挂在剑尖 | 握点量错，把护手当成柄 | 握点改到柄中段 |
| 跑步端枪姿势不对 | 跑步动作的手臂在甩 | 运行时合成 `run_rifle`：腿用 run、胸以上钉在抵肩姿态 |

验收方法同步改了：`/c/tmp` 下的拉伸检测脚本逐条动作数"被拉长 3 倍以上的边"，
现在抬枪 7 条、跑步 14 条、挥砍 2 条、死亡 16 条，集中在腋下，是轻微拉伸，近看已无尖刺和破洞。
袖子内侧切开后是开口的，验证台把角色材质设成双面，否则从背后看像碎片飘着。
验证台加了**右键拖动旋转 / 滚轮缩放 / 中键平移**，近看验收。

两条"顺带"的答案：Rodin Quad 模式 `quality=8000` 出约 16k 三角面，**管线里自动减到 7.8k**，
俯视看不出损失；Rodin 给的是 3 张 2048² 贴图，**压到 1024² WebP 后整只角色才 458 KB**——2048² 确实是浪费。

**实际走的路线与原计划的三处差异：**

| 原计划 | 实际 | 原因 |
|---|---|---|
| 买带动画的人形包 | 用 three.js 示例里的 Xbot（Mixamo 骨架 + idle/run/walk）当**权重捐赠者** | 不用上传 Mixamo，整条管线可在 Blender 命令行里重跑 |
| 包里自带攻击 / hit / death | `tools/poses.py` 程序化摆的关键帧 | Xbot 没有这几条；**它们是占位**，只证明"按握持切攻击"这条路通 |
| Draco + KTX2 | meshopt + WebP（`gltf-transform optimize`） | 体积已经远低于预算，少一个转码器依赖 |

**绑骨管线**（`tools/rig.py`，一条命令：`blender -b -P rig.py -- 角色.glb Xbot.glb 输出.glb`）：

1. 角色与捐赠者都归一到身高 1.8、减面到 7.8k
2. **逐侧网格搜索肩 / 肘角度，让捐赠者的 T-pose 手臂贴到角色的 A-pose 手臂上**（双向倒角距离打分）——
   Rodin 基本不给 T-pose，这一步不做，手臂权重会投到衣领上
3. Data Transfer 按最近面投权重，按骨骼距离修正袖子 / 腰侧的错投，手整只归 Hand；切开手臂与腿臀之间的面后再平滑，平滑完按切分归属再砍一次，裆下左右腿分开
4. **拟合姿态直接应用为静止姿态**（网格一个顶点都不动），捐赠者动画按世界空间逐骨复制重定向
5. 加 `socket_hand_r / l`：骨骼 +Y = 手指方向 = 武器 +Z，骨骼 +Z 朝掌面
6. 武器（`tools/weapon.py`）：原点移到握把、+Z 朝枪口、按真实长度缩放（狙击枪 1.0 m，剑 0.9 m）

**剩下的坑（都不阻塞 M1，记给 M5 批量跑时处理）：**

- **服装不能过膝**：过膝下摆没有可用的权重解，薇拉已改短夹克。这是 12 个角色的硬约束，不再是"优先"
- **手指不会弯**：手是刚体，握把是"夹在手里"而不是"握在手里"，近看能看出。要真握紧得换带指骨的手模（M3 美术替换）
- **跑步时腋下仍有少量碎边**（背后近看可见），俯视下看不出
- **程序化攻击 / hit / death 只是占位**，动作质量不够上线。M5 前要换成买的或动捕的动作包——
  动作包必须是 **Mixamo 骨架**，才能直接套进这条管线
- 武器握点是按网格剖面估的（狙击枪手枪握把 / 剑柄中段），换武器时目检一次即可，不是逐把调偏移

### M0 追加：改 Q 版体素

Rodin 高精网格那条路能过验收，但每个角色都要修权重、修到第三轮仍有碎边——**美术风格改为 Q 版体素、约 2.9 头身**（`00` A3、`05` §1.2）。
管线换成 `tools/voxel.py`（`blender -b -P voxel.py -- Xbot.glb 输出目录`）：

1. 部件表拼格子（5 cm），每块整块绑一根 Mixamo 骨，逐面顶点色、无贴图
2. Xbot 骨架**只挪关节位置**到 Q 版比例，骨骼朝向不动，idle / run / walk 的旋转键原样用；臀部位移按臀高比例缩
3. `poses.py` 的程序化攻击 / hit / death、`socket_hand_r / l` 照旧；Q 版手臂短，护木托点改近（0.2 m）
4. 狙击枪、剑也拼格子（2 cm），原点握把、枪口朝前

```
✅ 8 条动作全在，零权重混合 → 无拉伸、无粘连、无碎片（近看正 / 侧 / 背 6 个动作）
✅ vox_vera.glb 363 KB / 2,014 顶点 / 3,968 三角面（旧版 559 KB / 7.8k）
✅ 5 实例 + 武器 26k 三角面，GPU 0.11 ms
✅ 武器 vox_sniper 8 KB · vox_sword 6 KB，挂点与常量旋转不变
✅ 0 次 Rodin 生成
```

**12 人全量**（同一管线，改表不改代码）：

```
✅ 12 名角色 vox_<id>.glb，3,696–4,988 三角面，各 ≈420 KB（meshopt 后，多为 8 条动作的关键帧）
✅ 11 把主武器 vox_<武器>.glb，4–10 KB；各持自己的武器，攻击按握持类分四组：
   近战挥砍（剑 / 大剑 / 长枪）· 抵肩（狙击 / 喷火 / 冷冻 / 激光）· 单手平举（手枪 / 冲锋枪）· 投掷（手雷 / 回旋镖）
✅ 12 实例 + 武器 64k 三角面，GPU 0.19–0.50 ms，60 FPS（RTX 5080）
✅ 0 次 Rodin 生成
```

验证台（`proto/m0/index.html`）已换成 12 人阵列（「各自武器」为默认，也可全员换同一把）；旧的 `char_vera.glb` / `wpn_*.glb` 与 `rig.py` 留作对照。
**试看后第二轮**（用户反馈：头太大、近战没力度、长枪应该捅不该砍）：

- 头整组绕脖子缩到 0.8（`voxel.py` 的 `HEAD_K`），2.5 → 约 2.9 头身
- 近战拆成三条：`attack_melee1h`（剑，斜劈）、`attack_heavy`（大剑，双手过顶下劈）、`attack_thrust`（长枪，直线捅刺）。
  力度来自四件事：蓄力时胸口反拧（`twist`）、出手只用 2 帧且线性插值、打到底过冲后定格、臀部前压 + 双腿前后分开（`lunge`）。
  长枪多钉一个中间帧，否则逐骨插值会让枪头在送出途中往下画弧
- 顺手修了一个老 bug：Blender 场景缺省 24 fps，程序化关键帧按 30 fps 排，**所有程序化动作都慢了 1.25 倍**；
  现在导入 Xbot 前先把场景设成 30 fps
- 死亡改成被打飞：中弹后仰 → 离地往后飞、腿踢起 → 加速砸地 → 弹一下 → 瘫平（一侧膝盖弯起，不对称），落点在原地身后约 0.8 m
- 手雷 / 回旋镖出手后，手里的武器隐藏到收手时再出现（验证台按 `attack_throw` 的时间隐藏，不改 GLB）

剩下的：手是一块方块，没有握把的"握"——Q 版里这是风格，不是缺陷；程序化动作仍是占位。

**本轮 Rodin 消耗：11 次生成**（角色 8 次：5 次才拿到空手版、1 次改短夹克、v7 抽脸、v8 连体服定稿；武器 2 次；1 次早期测试）。
v7、v8 两次用的是 Gen-2.5-High 档，比默认档贵；M5 批量跑按默认档预算，只对脸不过关的角色升档。

## M1 — `core/` 逻辑骨架 + 对账测试

**产出：一个没有画面的、能跑完 15 分钟关卡的逻辑核心。**

### 任务

```
src/core/world.ts      世界状态：实体数组 + 网格哈希
src/core/tick.ts       固定步长主循环
src/core/combat.ts     伤害结算（与 sim/combat.ts 对账）+ 击退与控制判定（本轮新增）
src/core/spawn.ts      威胁预算刷怪（读 expandScene() 的子关卡，见下）
src/core/ai.ts         队员 AI 三层
src/core/squad.ts      队长控制 + 软硬牵引
src/core/terrain.ts    通行位掩码（本轮新增：4 位掩码，见 04-技术框架.md §2.3）
tests/reconcile.test.ts ★
```

> **`combat.ts` 本轮多了一层（击退与控制判定）。** 它读攻方击退力
> （武器 `knockback` × `knockMelee` / `knockRanged`）与守方稳固
> （英雄 `stab` / 僵尸表值），过一次饱和曲线，再问 `superArmor` 是否免位移。
> 这条判定与伤害**共用同一份输入**，所以它也必须进对账测试——
> 否则两边的击退命中率会各自漂移，而漂移只会在试玩时以"手感不对"的形式暴露。
>
> `terrain.ts` 也在这一步落地，但**只做掩码，不做摆放**：
> 位掩码的定义在 `src/data/scenes.ts` 的 `OBSTACLES`，
> M1 验证的是"四个判定各读对了一位"（`04-技术框架.md` §2.3）。

> **`spawn.ts` 的输入变了（本轮）**：旧版直接读 `run.ts` 的 `STAGES`，
> 新版读 `expandScene(scene, difficulty)` 的输出——即**某一个子关卡**的
> `{ threatBudget, dimWeights, spawnTable }`。
> `run.ts` 仍是一局的**时间结构**（3 阶段 × 5 分钟），
> `scenes.ts` 决定**这一局里刷什么**。两者的分工见 `04-技术框架.md` §2.1。

**寻路先不做**（M2 再加）。M1 里用"直线趋近"临时替代——
因为 M1 要验证的是**公式**，不是**空间**。

### 验收标准

```
□ node tests/reconcile.test.ts
  → 324 个用例全部在 1e-6 内相等，0 失败
  → 击退命中率同样在 1e-6 内相等（本轮新增的判定，与伤害共用输入）

□ node src/core/headless-run.ts
  → 能跑完 15 分钟，输出：击杀数 / 通关与否 / 三个 BOSS 的击杀秒数
  → 这三个数字与 sim 的读数【接近但不相同】（差异来自二维空间，符合预期）
  → 顺带打印击退命中率分布：霸体目标应为 0，高稳固目标应显著低于脆目标

□ 通行位掩码自检
  → 沙袋格：人能过 ✗ / 子弹能过 ✓；木墙格：四个判定全 ✗ 只有可破坏 ✓
```

### 关于"接近但不相同"

**M1 的验收不是"core 和 sim 跑出一样的结果"**，那是错的期待。
它们用的是不同的空间模型，结果必然不同。

要验收的是：**completion 级别的结论一致**——
sim 说"通关"，core 也该通关；sim 说"BOSS 3 用了 53 秒"，core 该在 40-70 秒之间。

如果 core 跑出来 BOSS 3 要 200 秒，那说明**二维空间让输出大幅度稀释了**，
这是个真实的设计发现，该回头改数值，而不是改 core 去迁就 sim。

> 这正是 `02-数值表.md` §10 说的那条边界的延续：
> sim 回答"自洽"，core 第一次能回答"在这套空间模型下还成不成立"。

**产出：能玩的东西。** 这是第一个能交给别人试玩的版本。

### 任务

```
src/core/path/flowfield.ts    流场寻路
src/core/path/astar.ts        队长点地寻路
src/core/terrain.ts           地形与通行性

### 验收标准

□ 同屏 300 只僵尸 @ 60fps（桌面端 GTX 1660 级别）
  → 用调试面板手动刷 300 只，跑 60 秒，帧时间 P99 < 16.6ms

□ core.tick() 单帧 < 6ms（含 300 僵尸的 AI + 流场查询）

□ 相机可以：鼠标右键旋转 / 滚轮缩放 / 俯仰角限制在 35°-80°

□ WASD 移动队长，4 名队员跟随且不穿墙

□ 僵尸能绕开建筑走到小队身边（流场生效，不是贴墙抖）
```

### 这个里程碑结束时必须做的第一件事

**找人试玩 10 分钟，专门验证 `00-决策清单.md` E1**：
> 玩家能否在混乱中看懂"谁在打谁"？

这是整个设计里最高风险的一条假设——**如果读不懂，游戏就不成立**，
而它没法靠数值或代码解决，只能靠 UI 和 AI 参数调。

## M3 — 完整关卡循环

**产出：一局完整的 15 分钟，含三个 BOSS、三档难度、结算。**

### 任务

```
src/core/boss.ts          BOSS 行为（含毒母的召唤、卡俄斯的混合刷新）
src/core/buff.ts          增益道具生成与拾取
src/core/quest.ts         任务 NPC（三种类型）
src/ui/squadbar.ts        ★ 本轮：命令栏（读 SQUAD_COMMANDS，见 04-技术框架.md §2.2）
src/ui/result.ts          结算界面
场景地形接入                （材质契约 §5 的方案，先接 2 个场景）
```

> **命令栏在这一步做，不在 M4。** 它属于"玩家能做什么"，
> 与元层无关；`SQUAD_COMMANDS` 是纯数据，M3 只需要一个
> "把命令的 `overrides` 写进队员 `AIProfile`"的循环。
> 押后到 M4 会有一个具体的代价：M3 的验收要靠试玩判断 15 分钟体感，
> 而命令栏会改变这个体感——分开做就等于**测了两次不同的东西**。

### 验收标准

```
□ 完整跑完一局 15 分钟，中途无崩溃、无卡死
□ 三个 BOSS 都能击杀，超时能正确判负
□ 五个增益道具都能拾取并生效
□ 队员死亡后永久损失，直到本局结束
□ 至少 2 个场景能加载，地形机制生效（水/沼泽/冰面/可破坏）
□ 三档难度跑出不同的刷怪表（对着 02-数值表.md §7.0.1 的丛林第 10 关核对）
□ 局内拾取能临时换上一把未解锁的武器（C3）
□ 结算界面正确显示：通关与否、击杀数、阵亡名单、用时
□ ★ 命令栏三个按钮都能生效：集火后全队打同一目标、重整阵型把队员拉回、
  紧密跟随让 leashRange 收窄到 12
□ ★ 命令栏的默认态是「自由」，且【不碰命令栏也能通关】——
  这是 A29 的验收项，见下
□ ★ 三种可破坏障碍：沙袋挡人不挡弹、铁丝网打掉后不留残骸、木墙能炸开
```

**倒数第三条是这个里程碑最容易做错的一条。** 命令栏的作用是让好玩家打得更快，
不是让普通玩家打得下去（`00-决策清单.md` A29）。验收方式是**跑一遍全程不切命令**，
看能不能通关——能，说明命令栏是效率旋钮；不能，说明它已经变成了操作门槛，
要往回砍（最省的一刀是把 `tight` 的覆盖值调得更温和，而不是删按钮）。

> **同一件事的另一个信号**：试玩时若玩家在**战斗中频繁切命令**，
> 说明它越过了那条线。这条比"能不能通关"更早暴露问题，要专门盯。

**三档难度在这一步就要验，不能留到后面。** 它改的是刷怪表构成
（`02-数值表.md` §7.0.1），如果 M3 结束时三档跑出来只差威胁速率，
说明难度层被写成了数值旋钮而不是构成旋钮——那要回头改，越晚越贵。

### 这个里程碑要回答的核心问题

**15 分钟是不是太长？**（`00-决策清单.md` C1）

C1 的结论是"保留 15 分钟，但留给试玩判断"。M3 是唯一能真正回答它的地方——
看试玩的人在第 12 分钟时是在战斗，还是在等结算。

**如果是在等结算**，动作是**降低 `LEVEL_COST`**（让成长更快），
而不是砍时长。理由写在 C1 里。

## M4 — 元层：世界地图 / 存档 / 双成长线

**产出：从"能打一局"变成"能一直打下去"。这是本轮架构调整的核心交付。**

### 任务

```
src/meta/profile.ts       存档 schema + 读写（纯 TS，只 import data/）
src/meta/unlock.ts        解锁判定：哪些场景/关卡/角色/武器可见
src/ui/worldmap.ts        三层：世界地图 → 场景详情 → 出击前确认
专精树 UI                 12 棵树的节点分配界面
src/ui/armory.ts          ★ 本轮：局外商店（读 SHOP，买断、全队共享；canEquip 校验出战配置）
技能点 / 军衔界面          ★ 本轮：点专精、买高级技能、看军衔进度
```

`Profile` 的 schema 与三条持久化规则定在 `04-技术框架.md` §2.1.1，本节不重复。

### 验收标准

```
□ 世界地图上 6 个场景、82 个子关卡全部可见可进
□ 出击前确认层显示该关的活跃维度提示（04-技术框架.md §2.1.3 第 3 层）
□ 通关一个子关卡后写入 Profile，刷新页面进度还在
□ 专精点能分配，且【分配后 computeDamage 的签名不变】——回归跑一遍
  node tests/reconcile.test.ts → 324 用例仍全过
□ 莉安顶层「战地复活」每局生效一次（C2 的唯一例外）
□ ★ 商店只卖种类：买完一把武器后，它的【阶】在本局仍由等级决定
□ ★ 军衔加身，属性表一个数不变——对着 §1 的六属性表逐项核对
□ ★ 高级技能要两把钥匙：军衔 4 级时买不到，5 级 + 4 技能点才能买
□ ★ 局内结算能把 money / honor 带出关卡，并入 Profile
```

**第四条是这个里程碑真正的验收项。** 前三条是功能，第四条是架构约束：
专精一旦能被写进伤害公式，`04-技术框架.md` §4 的对账测试就断了，
而那是整个数值体系的安全网。这条测试必须在接入专精**之前**就接进 CI。

**后四条是本轮新增的验收项，它们验的是同一件事：**
两条成长线给的是不是**新答案**而不是**新数字**。
商店只卖种类、军衔不碰属性、高级技能要两把钥匙——三条合起来才构成
"金钱给选项、技能点给深度、时间给所有人"这个分工
（`00-决策清单.md` A25 / A26 / A27 / A28）。
任何一条破了，"卡住只能换阵容"这个前提就会被"打不过就回去刷"顶替掉。

### 这个里程碑要回答的核心问题

**`00-决策清单.md` E8/E9/E11**：专精点怎么给、解锁曲线怎么排、难度档怎么开。

三条的正确答案都取决于试玩，而试玩只有在 M4 之后才拿得到完整循环。
所以 M4 先按最保守的方案落地（通关给点、并列可选、难度独立可选），
把三条留成可调参数，等试玩数据再定。

> **一条要提前知道的风险**：M4 是唯一有可能**破坏本轮设计目标**的里程碑。
> 只要局外存在可刷的数值，"打不过就回去刷"这条路就打开了，
> 而整个设计的前提是"卡住只能换阵容"。守住它的不是文档，是 §2.1.2 的
> `SpecEffect` 联合类型——**别为了省事给它加一个 `damageMul` 变体。**
